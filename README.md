# Event Management System — Full Stack Application

## Опис проєкту

**Event Management System** — вебзастосунок для організації та управління подіями.

Проєкт складається із серверної частини (REST API) та клієнтської частини (React-застосунок), які взаємодіють між собою через HTTP-запити та Socket.IO.

Backend забезпечує реєстрацію й авторизацію користувачів, розмежування прав доступу, управління подіями, локаціями, учасниками, реєстраціями, квитками та розкладом.

Frontend реалізований на React і TypeScript та забезпечує користувацький інтерфейс для взаємодії із серверною частиною.

## Встановлення та запуск

### Вимоги
- Node.js 20 або новіше
- npm
- PostgreSQL (локально або через Docker)

### 1. Клонування репозиторію

```bash
git clone https://github.com/Yotikovich/Lab_1_6_WEB.git
cd Lab_1_6_WEB
```

### 2. Встановлення залежностей Backend

У кореневій папці проєкту виконати:

```bash
npm install
```

### 3. Налаштування змінних середовища Backend

Створити файл `.env` у корені проєкту на основі `.env.example`.

Приклад налаштувань:

```env
DATABASE_URL="postgresql://USER:PASSWORD@localhost:5432/event_management?schema=public"
JWT_ACCESS_SECRET="your_long_random_access_secret"
JWT_REFRESH_SECRET="your_long_random_refresh_secret"
PORT=3000
```

Замість `USER` і `PASSWORD` указати власні облікові дані PostgreSQL. Для JWT-секретів використати довгі випадкові значення.

Файл `.env` не можна публікувати або додавати до Git.

### 4. Підготовка бази даних

Переконатися, що PostgreSQL запущений, а база даних `event_management` створена.

Згенерувати Prisma Client:

```bash
npm run db:generate
```

Застосувати міграції:

```bash
npm run db:deploy
```

Якщо для локальної розробки використовується синхронізація схеми без міграцій, можна застосувати команду:

```bash
npx prisma db push
```

### 5. Запуск Backend

Режим розробки:

```bash
npm run dev
```

За замовчуванням API працює за адресою:

```text
http://localhost:3000
```

Перевірка стану сервера:

```text
http://localhost:3000/api/health
```

Документація Swagger:

```text
http://localhost:3000/api-docs/
```

### 6. Встановлення залежностей Frontend

Перейти до каталогу клієнтської частини:

```bash
cd client
npm install
```

### 7. Налаштування змінних середовища Frontend

Створити файл `client/.env` або скопіювати `client/.env.example`:

```env
VITE_API_URL=http://localhost:3000/api
VITE_SOCKET_URL=http://localhost:3000
```

### 8. Запуск Frontend

```bash
npm run dev
```

Після запуску Vite покаже локальну адресу застосунку, зазвичай:

```text
http://localhost:5173/
```

### 9. Перевірка та збірка Frontend

Перевірка коду:

```bash
npm run lint
```

Production-збірка:

```bash
npm run build
```

Попередній перегляд production-збірки:

```bash
npm run preview
```

## Документація API

Після локального запуску сервера документація доступна за адресою:

```text
http://localhost:3000/api-docs/
```

Swagger UI дозволяє переглядати описані маршрути, параметри запитів, структуру даних і відповіді API. Для захищених операцій необхідно авторизуватися за допомогою Bearer-токена.

## Основні маршрути API

### Авторизація — `/api/auth`
- `POST /api/auth/register` — реєстрація користувача.
- `POST /api/auth/login` — вхід у систему.
- `POST /api/auth/refresh` — оновлення токенів.
- `POST /api/auth/logout` — вихід із системи.
- `POST /api/auth/change-password` — зміна пароля.
- `GET /api/auth/me` — отримання даних поточного користувача.

### Події — `/api/events`
- `GET /api/events` — отримання списку подій.
- `POST /api/events` — створення події.
- `GET /api/events/:id` — отримання інформації про подію.
- `PUT /api/events/:id` — редагування події.
- `DELETE /api/events/:id` — видалення події.

### Локації — `/api/events/venues`
- `GET /api/events/venues` — отримання списку локацій.
- `POST /api/events/venues` — створення локації.
- `PUT /api/events/venues/:id` — редагування локації.
- `DELETE /api/events/venues/:id` — видалення локації.

### Учасники та реєстрації
- `GET /api/events/participants` — список учасників.
- `POST /api/events/participants` — створення або оновлення даних учасника.
- `GET /api/events/registrations` — список реєстрацій.
- `PATCH /api/events/registrations/:id/cancel` — скасування реєстрації.
- `POST /api/events/:id/registrations` — реєстрація учасника на подію.

### Квитки
- `GET /api/events/:id/ticket-types` — список типів квитків події.
- `POST /api/events/:id/ticket-types` — створення типу квитка.

### Розклад
- `GET /api/events/:id/schedule` — отримання розкладу події.
- `POST /api/events/:id/schedule` — додавання пункту розкладу.

Детальні параметри запитів і схеми відповідей наведені у файлі `API_DOCUMENTATION.md` та Swagger UI.

## Взаємодія в реальному часі — Socket.IO

Socket.IO використовується для обміну подіями між сервером і підключеними клієнтами без необхідності постійно надсилати HTTP-запити.

Під час встановлення з'єднання клієнт передає JWT, а сервер перевіряє токен перед підключенням.

Механізм Socket.IO також може використовуватися для оновлення статусу користувачів і синхронізації подій у межах відповідних кімнат.

## Безпека та доступ

- Паролі користувачів зберігаються у вигляді хешів Argon2id.
- Для автентифікації використовуються JWT access- і refresh-токени.
- Захищені API-маршрути перевіряють авторизацію користувача.
- Вхідні дані перевіряються за допомогою Zod.
- Організатор керує власними подіями відповідно до правил доступу системи.
- Адміністратор має розширені права керування.
- Для реєстрації перевіряється доступність квитків і місткість події.

## Обмеження

- Інтеграція з платіжними системами не передбачена.
- Квитки створюються як записи в базі даних з унікальними кодами.
- Для повноцінної роботи потрібне налаштування PostgreSQL та змінних середовища.
